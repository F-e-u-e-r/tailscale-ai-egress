# Stability and Compatibility (1.x)

Version 1.0 freezes the product surface so the project is safe to recommend and
depend on. This page is the contract for the 1.x series.

## Versioning

- The toolkit follows [Semantic Versioning](https://semver.org).
- The single source of truth for the version is the [`VERSION`](../VERSION) file,
  mirrored by `__version__` in [`scripts/policy_tool.py`](../scripts/policy_tool.py).
  A unit test enforces that they match.
- Every shell entrypoint and `policy_tool.py` prints it via `--version`, e.g.
  `tailscale-ai-egress bootstrap.sh 1.0.0`.
- Within 1.x, no breaking changes to anything listed under "Frozen surface"
  below. Such changes wait for a 2.0.

## Frozen surface

### Stable CLI entrypoints

These commands, their documented flags, and their `--json` schemas
(`schema_version: 1`) are stable for 1.x:

- `bootstrap.sh`
- `check-client-routes.sh`
- `diagnose.sh`
- `enable-exit-node.sh`
- `disable-exit-node.sh`
- `restore-connector.sh`
- `rollback.sh`
- `scripts/policy_tool.py` (`snippet`, `validate`, `merge`, `diff`, `plan`,
  `apply-plan`, `list-plans`, `restore-plan`, `restore`, `domains`)

New optional flags may be added. Existing flags, their meanings, and the JSON
output shape will not change incompatibly within 1.x. The `policy_tool.py apply`
command has been removed after its one-release deprecation; use `plan` +
`apply-plan` (running `apply` now prints that pointer and exits non-zero).

### Plan manifest schema

The policy plan manifest `schema_version` major version is frozen at `1`. Plan
bundles generated by 0.4 use the same major version and remain readable by 1.x
tooling. `policy_tool.py` refuses manifests whose major version does not match,
with a clear "regenerate the plan" message.

### Built-in domain list

The built-in domain list is `common`. Its contents may gain or adjust provider
domains in minor releases, but the `common` selection and `--domain-pack common`
remain stable. Custom domains are supported with `--domains-file`. The
standalone fallback list embedded in `check-client-routes.sh` is kept in sync
with `policy/default-ai-domains.json` (a unit test enforces this).

## Recommended modes (unchanged in 1.x)

- **Manual Guided Mode is the recommended path.** `bootstrap.sh` defaults to
  generating a policy snippet for manual paste and never modifies your tailnet
  policy unless you opt in.
- **Advanced Admin Automation is opt-in only.** Its prompt always defaults to
  `N`, even when credentials are present in the environment.

## Deliberately out of scope for 1.x

To keep the trust boundary small, 1.x will not add:

- A GUI.
- Provider API provisioning or automatic VPS purchasing.
- Telemetry or any project-operated server.
- Additional proxy protocols (Shadowsocks, sing-box, Xray, etc.).

## Supported platforms

- **Server OS:** Ubuntu/Debian first. Other Linux distributions are best-effort
  unless already verified. See [Validation-Matrix.md](Validation-Matrix.md).
- **Client OS:** macOS (App Store or standalone Tailscale) and Linux (normal TUN
  mode, plus a userspace-networking warning path).

## Install provenance

The conservative, recommended install path is to clone a reviewed tag and run
`./bootstrap.sh` directly:

```bash
git clone https://github.com/F-e-u-e-r/tailscale-ai-egress.git
cd tailscale-ai-egress
git checkout v1.0.0
./bootstrap.sh
```

`install.sh` remains available for convenience. Outside a checkout, it downloads
the tagged release artifact for `VERSION` (or `TAILSCALE_AI_EGRESS_VERSION`) and
verifies it against that release's `SHA256SUMS` before running `bootstrap.sh`.
When `gh` (>= 2.93.0) is present it also verifies the tarball's build-provenance
attestation against the release workflow on the exact tag; a missing/older/
unrecognized `gh` degrades to checksum-only, and `TAILSCALE_AI_EGRESS_SKIP_ATTESTATION=1`
opts out (see [Configuration.md](Configuration.md#remote-installer-installsh)).
Setting `TAILSCALE_AI_EGRESS_BRANCH` switches to a development branch archive
and prints an unverified-download warning.

Prefer cloning a reviewed tag and verifying the `SHA256SUMS` attached to the
release yourself when provenance matters.
